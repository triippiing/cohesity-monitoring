Auth & conventions

Base paths

  • v2: https://<cluster-vip>/v2/...
  • v1: https://<cluster-vip>/irisservices/api/v1/public/...
  • Helios (SaaS/on-prem MCM): same v2 paths, plus /v2/mcm/* (e.g. /v2/mcm/alerts, /v2/mcm/stats/alerts-summary). Send an accessClusterId header to target one cluster.

Auth options (from the v2 spec security schemes)

  • API key: header apiKey: <key>. Best choice for an exporter: no login round-trip, no token expiry handling. Create it on a dedicated user.
  • Bearer token: POST /v2/access-tokens with {"username","password","domain":"LOCAL"} returns accessToken. Then send Authorization: Bearer <token>. v1 equivalent: POST /public/accessTokens. This POST is the only one the exporter would ever need, and it changes nothing.
  • Session: POST /v2/users/sessions returns session-id header. Meant for UI flows; skip it.

Least privilege

  • Create a local user, e.g. svc_prometheus, with the built-in Viewer role. Enforcement is server-side, so no write is possible even if a POST slips into the code.
  • Multi-tenant clusters: add includeTenants=true where offered, or tenant objects are hidden.
  • Use the cluster VIP, not a node IP, so scrapes survive node failover.

Conventions to handle in the exporter

  • Timestamps are microseconds (*Usecs), except time-series stats, which use milliseconds (*Msecs). Export everything as seconds.
  • Enums use a k prefix (kVMware, kPhysical, kOracle). Strip it for labels.
  • Pagination: paginationCookie/maxResultCount on groups and runs, cookie/count elsewhere.
  • useCachedData=true serves from a read replica (~15s lag). Use it on every scrape that offers it to keep load off the primary.
  • Self-signed cert by default, so pin the cluster CA in the exporter rather than disabling verification.

Suggested build order

Dashboard row 1 · estate health

/v2/stats/cluster-storage, /v2/clusters/state, v1 /public/cluster/status, /v2/alerts-summary, /v2/clusters/nodes. That covers capacity %, version, stopped services, critical alert count and offline disks: five calls per cluster every 5 minutes.

Row 2 · backup outcome & SLA

/v2/data-protect/protection-groups?includeLastRunInfo=true plus /v2/stats/protection-runs, plus v1 /public/stats/protectionRuns/lastRun for SLA %. Replication and archival status come from the same group payload.

Row 3 · efficiency & growth

/v2/storage-domains?includeStats=true for dedup and compression per domain, v1 /public/stats/consumers for top consumers, v1 /public/stats/vaults for archive usage. Grafana's deriv()/predict_linear() on used bytes gives a days-to-full panel.

Row 4 · coverage & sources

v1 /public/stats/protectionSummary for protected vs unprotected, /v2/data-protect/sources/registrations for source connectivity, /v2/data-protect/objects/last-run for a failing-objects table.

# example alert rules
- alert: CohesityRPOBreach
  expr: time() - cohesity_pg_last_run_end_timestamp_seconds{} > 26*3600 and on(pg) cohesity_pg_active == 1 and on(pg) cohesity_pg_paused == 0
- alert: CohesityCapacityHigh
  expr: cohesity_cluster_used_bytes / cohesity_cluster_capacity_bytes > 0.80

Cardinality: labels per protection group are fine (tens to hundreds). Labels per object (every VM or DB) can mean thousands of series per cluster. Keep object-level data to a 15–60 minute job, or expose it only for objects in a failed or SLA-violated state.
